## ADR-008: free live-data stack, personal use
24 October 2026 · accepted by the user (personal, non-commercial use). Google offers no flight API. ## ADR-012: time and date rules
25 October 2026 · owner's rules, implemented. Flight times are instants (ISO UTC) shown in each airport's own IANA zone via Intl, so BST/GMT and every other clock change come from the zone database; a time or zone that cannot be read shows "Not available", never a guessed time, and a time without a zone is labelled UTC, not "local". The default search date is the UK (Europe/London) date (`ukDate` in src/flightFormat.ts). The requested date is the departure date in the departure airport's local time: the PHP schedule window accepts yesterday-to-+3-days at any place on Earth (UTC-12..UTC+14) and `filterByDepartureDate` matches the airport-local date. Owner-console counters are bucketed by UK calendar day (Metrics::day; ranges step in calendar days so a 23- or 25-hour clock-change day is listed once); files written before this change are keyed by UTC day, so up to one hour per summer day (00:00-01:00 BST) of older data sits on the previous day. The AeroDataBox monthly allowance counters stay on UTC months.

## ADR-013: abuse limits on public writes (25 Oct 2026)
Decision: the two unauthenticated write routes accept only same-site JSON; contact is limited per visitor (IPv6 /64), emails are capped site-wide per hour, and storage has a hard ceiling. Why: a per-address limit alone is defeated by IPv6 rotation and by other sites making visitors' browsers post the form. Cost: none for real users; scripted clients must send `Content-Type: application/json`.

## ADR-014: shareable flight links and offline fallback (25 Oct 2026)
Decision: a searched flight gets the address `#/flight/<number>/<date>` (Share copies it); the last six results stay on the device and are shown only when the network fails, always labelled "last fetched at". Calendar files are generated in UTC and only when both times are known. Why: people share flights and lose signal at airports; accuracy rule: never show stored data as live.

## ADR-015: public website at `/`, app at `/app/` (25 Oct 2026)
Decision (owner, 25 Oct 2026): the public website is rendered by PHP from CMS content at `/` and the public paths; the React app moves to `/app/`. Why: search engines and link previews need readable HTML, and the CMS can only edit the home page without a code release if the server renders it. How old links keep working: `site.js` forwards `/#/flight/...` and other app hash routes, and installed apps that open `/` (standalone display mode), to `/app/`. The manifest keeps `id: '/'` so existing installs keep their identity; `start_url` is `/app/`; the service worker stays at `/sw.js` (scope `/`) and falls back only for `/app/`. `.htaccess` sends the known site paths to `site.php` before the real-file check, because additive releases leave the old static pages on the server. Cost: two entry points (site.php, app/index.html).

## ADR-016: file-based CMS in private `var/content` (25 Oct 2026)
Decision (owner chose the recommendation): CMS content, drafts, history and media are JSON and image files in the private folder, like the existing checklists and enquiries; no database. Why: one editor, small volumes, the project has no database, and the brief said not to change the database architecture for a template. Writes take one lock and use atomic renames; history is immutable. If several editors or large volumes appear, move to cPanel MariaDB with restricted users (SCHEMA.md).

## ADR-017: safe Markdown, no HTML, for every CMS text (25 Oct 2026)
Decision: the CMS stores a Markdown subset, rendered server-side by a small escaping renderer that can only produce a fixed tag set and safe links. Why: the brief forbids editors publishing executable HTML/JavaScript; an HTML sanitiser is harder to get right than a renderer that never passes HTML through. Existing pages were converted once (scripts/seed-content.mjs) and compared by tests (headings, links, legal wording). One reserved link, `#cookie-settings`, reopens the cookie choice.

## ADR-021: gates and key times up front; weather and Discover beside the flight; web links only as links (1 Nov 2026)
Context: the owner could not see boarding and arrival gates, take-off and landing times, or when boarding starts and the gate closes (they were inside tabs or not shown), wanted weather and destination discovery as a first feature, and asked whether Bright Data could fill missing information.
Decision: (1) A "Gates and key times" panel under the summary shows departure gate, boarding starts, gate closes, take-off, landing, reaches the gate, arrival gate and baggage belt. Provider values are shown as reported; airlines rarely publish boarding and gate-closing times to data feeds, so those are worked out from the departure time (30/15 min short-haul, 40/20 from 3 h, 50/20 from 6 h) and badged "Typical"; take-off and landing without a runway time are typical too (+15 / −10 min). (2) Weather (now, at landing, 4 days) and Discover sit beside the flight from 1280px and right after the key times below that; the Weather and Destination tabs are gone. Discover uses the hand-written guides where they exist, otherwise Wikivoyage then Wikipedia (free, CC BY-SA, credited; cached a week). (3) Bright Data: a live test search for BA117 returned tracker snippets with mixed dates (including a flight from four days earlier), and the trackers' terms forbid reuse. So the server returns search-result links only (trackers dropped), shown as "Latest from the web… not checked by Flightdeck", only while the gate is unknown, cached 15 minutes per flight, capped per day, and OFF until the owner adds `brightdata_key` and `brightdata_zone` (it costs money).
Rejected: parsing gates or times out of search snippets (a wrong gate is worse than none); scraping FlightAware/Flightradar24 pages.

## ADR-022: sign-in fails closed; per-user allowances for paid look-ups (1 Nov 2026)
Context: the go-live security review (docs/AUDIT.md, 1 Nov) found that a missing or mistyped `clerk_issuer` (a trailing slash was enough) quietly switched sign-in off and opened `/flights`, `/weather`, `/place` and `/web-check`, including paid AeroDataBox look-ups, to anyone; that one signed-in user could use up the site's shared AeroDataBox and Bright Data allowances; and that the Bright Data daily cap could be overrun by simultaneous searches (reproduced: 116 paid searches against a cap of 40). The owner asked for every finding to be fixed.
Decision: (1) Without a valid issuer, every protected route answers 503; only the local test switch `FLIGHTDECK_AUTH=off` (server environment, never a request or config.php) opens the look-ups, and the checklist and console stay refused even then. A trailing slash on the issuer is ignored. Supersedes the part of ADR-010 where an unset issuer left the look-ups open. (2) Each signed-in user may cause at most half the hourly AeroDataBox cap (default 6 of 12; `aerodatabox_user_hourly_calls`) and 20 Bright Data searches a day (`brightdata_user_daily_cap`); the owner is exempt; cache hits cost nothing; over the limit the flight still shows live data with a note. (3) Allowance counters are read and written under a lock; waits for a provider lock give up after 10 s with "busy" (`provider_lock_wait_ms`).
Rejected: per-visitor IP limits only (already in place; they do not stop one account on many networks); blocking the owner too.

## ADR-023: the deploy waits for the full CI gate; deploy-on-push stays (8 Nov 2026)

## ADR-025: gate, terminal, belt and boarding facts read from the web, checked by code and always labelled (9 Nov 2026)
Context: the owner asked on 9 Nov 2026 for "the right information" on the Journey page, found by AI or Bright Data and updated in real time (their BA75 screenshots showed gates, terminal and belt "Not reported yet"). They decided the extractor (AI through the Anthropic API, model Sonnet 5.5, and they hold the key) and delegated the ADR-003 amendment and the caps to me. ADR-003 said web results are links to check, never copied into gate or time fields. Evidence for care: the Bright Data results for BA75 on 9 Nov were for 7 and 8 Nov, so a snippet can be right about another day; AeroDataBox often has no gate (for example BA117, 8 Nov); tracker sites forbid scraping (ADR-008) and stay skipped.
Decision:
1. **ADR-003 is amended, not repealed.** A value from the web may be shown for six things only: departure gate, departure terminal, arrival gate, arrival terminal, baggage belt and boarding time. Never for departure, arrival, take-off or landing times, status, delay, cancellation or position: a wrong time can make someone miss a flight, and those come from the providers only.
2. **The AI proposes; the code decides.** Claude (`claude-sonnet-5-5`, structured output, low effort) is shown the Bright Data result text and returns findings: a field, a value, which result, and the exact words it relied on. `WebFacts::validate` (plain PHP) accepts a finding only if all of these hold: the quote appears word for word in that result; the result names this flight's number (BA75, BA 75, BA075; not BA750 or BA175); the result mentions the flight's date on that side (the departure day for departure facts, the arrival day for arrival facts, in local time) and, if it lists several days, the quote itself holds the right one; the airport on that side is named and the result is about that side (departures or arrivals) while the quote is not about the other; the value sits straight after its label (Gate, Terminal, Belt/Carousel/Reclaim, Boarding) and has the shape of such a value (so "-", "TBC", a terminal digit or a departure time cannot become a gate); the link is https and not a tracker or social site. Anything else is dropped without a message. Each of those rules has a test that fails if the rule is removed (mutation-checked).
3. **Display.** The provider's value always wins; a web value only fills a gap. It is labelled "From the web", with the site as a link, the time it was checked and the sentence "Not confirmed by the airport: follow its screens", and it looks the same on Key times, the Journey and the Airport tab. It never counts as "done" in the Journey. If the server has the feature off, is capped or fails, nothing changes on screen.
4. **Refresh.** The app asks only when a search is worth paying for (`webNeeds`): links from 24 hours before departure to 3 hours after arrival; facts from 5 hours before departure until 30 minutes after, and from 2 hours before landing until 2 hours after; never for a cancelled flight; a boarding time alone does not start a search. While the page is open and visible it asks again every 5 minutes. The server caches a search for 10 minutes (was 15), and Claude's answer for 6 hours keyed by the result text, so unchanged results cost no second call; a failed call is not retried for 2 minutes.
5. **Caps (my decision).** Bright Data: 200 searches a day and 40 per signed-in user (was 150 and 20), because a flight in its window can use about 30 searches at a 10-minute cache and the old per-user cap would have been used up by one flight. Claude: 150 calls a day (`anthropic_daily_cap`). ASSUMPTION: a call is about 1,500 input and under 1,000 output tokens, roughly one US cent at the published Sonnet 5.5 prices ($2 and $10 per million tokens), so the cap bounds the spend at about $1.50 a day; the real figure is in the owner's Anthropic console. The owner console's Costs page shows both counts. Each can be switched off: remove the key, or set `'web_facts' => false`.
6. **Privacy.** Anthropic becomes a processor of public search-result text, the flight number, the date and the airport codes. No name, email, IP address, account or saved trip is sent. The privacy page names it (this change). Check Anthropic's current API data terms when switching on.
7. **Key handling.** The key goes into the private `config.php` only, through `scripts/set-anthropic-key.sh` (hidden prompt, SSH stdin, backup, `php -l`, never printed). It is never in chat, the repository or the browser.
8. **Implementation notes.** The call is made over HTTP through the project's own `Http::request`, not the Anthropic PHP SDK: the PHP API has no Composer and no `vendor/` folder, and this is one endpoint. Request: `anthropic-version: 2026-10-21`, `output_config.format` (JSON schema) and `effort: low`; no sampling parameters, no forced tool choice, no disabled thinking (Sonnet 5.5 rejects those). Refusal fallbacks are not used: a refusal or a cut-off answer simply gives no facts.
Rejected: rules only (breaks when a page changes and finds little); trusting the model without the check; any scraping of tracker sites (ADR-008); fetching whole pages through the Web Unlocker zone in the first version (more cost, mostly script-built pages); showing departure or arrival times from the web.
Consequence: yield is unknown until it runs on the live site: the validator is strict on purpose, so expect it to fill some gates and leave others empty. Review Provider health and the Costs page after the first week; if too little is found, the next step is the Web Unlocker zone for the airport's own page, not a looser check.
